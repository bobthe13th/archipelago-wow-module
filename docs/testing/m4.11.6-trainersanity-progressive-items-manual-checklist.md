# M4.11.6 — Trainersanity Progressive Items: Manual Verification Checklist

Automated coverage: the pure gate decision (`ShouldBlockTrainerTeach`, Task 1), the trainer-purchase
interception script (`ArchipelagoTrainerPurchaseScript`, Task 3), the decoupled `trainer_purchase_attempt`
trigger and `learn_next_chain_rank` delivery emission (Tasks 4/6/7, `generate_content.py` +
`test_generate_content.py`), and the content extractor's chain-grouping and same-display-name
disambiguation (`extract_trainer_spells.py` + `test_extract_trainer_spells.py`) all have real unit/doctest
coverage. Everything below requires a live worldserver with this module built, connected to a real AP
session, and cannot be exercised any other way.

Prerequisite: a live worldserver with this module built, connected to a real AP session with at least one
multi-rank class spell (e.g. Frostbolt) in the item pool.

## 1. Trainer purchase interception (no learn, no gold, correct feedback)

- [ ] Visit a class trainer for a spell you're eligible to learn (level/skill/prior-rank requirements met)
      but have not received via AP yet. Click to purchase it.
  - Expected: gold is NOT deducted, the "you have learned" success sound/visual do NOT play, and you see
    the "this technique lies elsewhere in the multiworld" chat message.
- [ ] Confirm the AP client shows exactly one "location checked" event for that trainer visit, and does not
      show a second one later when the corresponding item is actually received.

## 2. Progressive item delivery

- [ ] Receive the "Progressive `<Spell>`" item for that chain from the multiworld (via `.ap` test-send or a
      real generation).
  - Expected: you immediately know rank 1 of that spell (or the next un-granted rank, if some ranks were
    already granted), with no trainer visit required.
- [ ] Receive a second copy of the same "Progressive `<Spell>`" item.
  - Expected: you now know rank 2.

## 3. Vanilla-parity edge cases

- [ ] Return to the trainer after already knowing a rank via AP.
  - Expected: the trainer UI shows that rank as already known (grayed out / "Known"), matching vanilla
    behavior -- this path never re-reaches the new hook (`Trainer::CanTeachSpell` already returns `Known`
    before `OnPlayerCanTrainerTeachSpell` is ever called).
- [ ] Log out before an AP item grant is applied, receive the item while offline, log back in.
  - Expected: the spell is granted on login (via `APSpellGrant::ApplyPendingGrants`), same as every other
    offline-queued grant in this module.

## 4. Same-display-name chain disambiguation (regression coverage for a real content-authoring bug)

Two different rank chains can share the same spell display name in real WotLK data (confirmed against the
live world DB while regenerating this milestone's content: Death Knight's and Warlock's "Death Coil" are
distinct chains). `extract_trainer_spells.py` now disambiguates any chain names that collide by appending
the teaching class(es) -- e.g. "Progressive Death Coil (Death Knight)" vs. "Progressive Death Coil
(Warlock)" -- verified structurally by `test_extract_trainer_spells.py`, but the real in-game item names are
worth a spot-check:

- [ ] In the generated item pool / a real AP data file, confirm both "Progressive Death Coil (Death
      Knight)" and "Progressive Death Coil (Warlock)" exist as two distinct items (not a single collapsed
      or overwritten entry).
- [ ] Receive one of the two Death Coil items in-game as a Death Knight or Warlock. Confirm it grants a rank
      of the correct class's Death Coil chain, not the other class's.

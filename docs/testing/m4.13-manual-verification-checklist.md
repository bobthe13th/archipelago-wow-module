## 1. `.ap missing` — paginated remaining-locations listing

- [ ] Connect a live worldserver to a real AP room with an in-progress seed
      that has more than 20 remaining (unchecked) locations.
- [ ] Run `.ap missing` as a normal player. Confirm:
  - The header line reports the correct total remaining count and "page 1".
  - Exactly 20 location names are listed (or fewer, if the header total is
    under 20).
  - If more than 20 remain, a trailing `Use '.ap missing 2' for more.` line
    appears.
- [ ] Run `.ap missing 2` (and further pages as needed). Confirm each page
      shows the next 20 (non-overlapping) locations, and the last page's
      "more" hint disappears once `startIndex >= missing.size()`.
- [ ] Run `.ap missing <n>` for an `<n>` past the last page. Confirm the
      "page N is past the end (M location(s) remaining total)" message, not a
      crash or an empty page.
- [ ] Among the listed locations, confirm:
  - A Vendor Inventories or Quest Rewards location shows its real synthesized
    player-facing name (e.g. `"Alice's Sword of Might"`), sourced from
    `Archipelago::ItemDisplay::GetSynthesizedDisplayData()` — i.e. the exact
    name a player would see in-game on that vendor/quest reward.
  - A location from every other family (recipes, trainer spells,
    containersanity, gathersanity, ...) shows its plain content-table name
    (e.g. `"Reach Level 47"`), sourced from `Archipelago::Locations::AllLocationNames`.
- [ ] Run `.ap missing` again once the seed has 0 remaining locations left.
      Confirm `"Archipelago: no locations remaining."` rather than an empty
      or malformed page.
- [ ] Run `.ap missing` while disconnected from the AP server (before
      connecting, or during a `.ap port`-triggered reconnect window). Confirm
      `"Archipelago: not connected."` rather than stale/empty data.

## 2. `.ap hint <item>` — AP server-interpreted hint request

- [ ] Run `.ap hint <exact item name>` against a real AP room, item name
      copied verbatim from a real slot on this seed. Confirm:
  - The client immediately gets `"Archipelago: hint requested, watch chat for
    the response."`
  - Shortly after, a server-wide chat broadcast appears (via
    `SendServerMessage(SERVER_MSG_STRING, ...)`, `ArchipelagoWorldScript::OnUpdate`
    draining `onPrintJsonReceived`) containing the AP server's `PrintJSON`
    hint response.
  - Every currently-online player sees the broadcast, not just the requester
    (per design spec Sec2's "display to all currently online players").
- [ ] **Known, intentionally-scoped limitation** (see the M4.13 plan's "Real
      corrections" section, and `ParsePrintJSONText`'s own doc comment):
      confirm that any `player_id`/`item_id`/`location_id`-typed part of the
      hint response renders as a **raw numeric id**, not a resolved name —
      e.g. `"...42's item is at 1234..."` rather than `"...Alice's item is at
      Reach Level 47..."`. This module has no cached per-game `DataPackage` to
      resolve those ids with; building that resolver is real, separate,
      out-of-scope future work. Literal narrative text parts (e.g.
      `"[Hint]: "`, `". "`) should render correctly as-is.
- [ ] Run `.ap hint` with no argument. Confirm `"Usage: .ap hint <item name>"`.
- [ ] Run `.ap hint <item>` while disconnected. Confirm `"Archipelago: not
      connected."` and no packet is sent.

## 3. `.ap port <n>` — GM-only live reconnect

- [ ] Stand up a second local AP test room/server on a different port than
      the one the worldserver is currently connected to.
- [ ] As a GM-flagged account, run `.ap port <n>` with the second room's port.
      Confirm:
  - `"Archipelago: reconnecting to port <n>..."` is echoed immediately.
  - The realm connects to the new room's `RoomInfo`/`Connected` handshake
    within roughly `Archipelago.ReconnectMinSeconds` (default 2s) — i.e. the
    backoff-reset in `APClient::Reconnect` (`_currentBackoffSeconds = 0`) is
    actually taking effect, not carrying over a larger backoff from an
    earlier unrelated drop.
  - No worldserver process restart occurred (`.ap status` reflects the new
    room's connection state without a `.server restart`/relog of the
    process).
  - `.ap status` reports `"connected"` once the new room's handshake
    completes.
- [ ] As a **non-GM** account, run `.ap port <n>`. Confirm the standard
      AzerothCore "you do not have permission" (or equivalent
      `SEC_GAMEMASTER`-gated) rejection — the command must not execute at
      all, matching the `ChatCommandTable`'s `SEC_GAMEMASTER` entry.
- [ ] Run `.ap port` with no argument (as a GM). Confirm `"Usage: .ap port
      <port number>"`.
- [ ] Run `.ap port notanumber` (as a GM). Confirm `"Archipelago: 'notanumber'
      is not a valid port number."` rather than a crash or silent no-op.

## 4. Guard-clause cross-check

- [ ] `.ap hint`/`.ap port` both correctly report `"not connected"` (`.ap
      hint`) or accept the request even when disconnected (`.ap port` doesn't
      require an existing connection — it's meant to establish/redirect one;
      confirm it degrades gracefully, i.e. no crash, if `ArchipelagoManager`'s
      `_client` was never constructed at all, e.g. `Archipelago.Enabled=0`).
- [ ] `.ap missing`/`.ap hint` both require `HandshakeComplete`, not merely
      "a `_client` exists" — confirm neither responds with stale/empty data
      while still `Connecting`/`Reconnecting`.
